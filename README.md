## 오늘 공부한 내용

### 키워드1: 로그인 UX와 프론트엔드 디테일

**개념 정리**

URL에서 직접 로그인해야 하는 사이트는 면접관에게 불편함을 준다. 그래서 포트폴리오에는 아이디와 비밀번호를 지정해 둔 링크를 만들어, 클릭하면 바로 이동해서 볼 수 있게 해주면 좋다. 프론트엔드의 핵심은 얼마나 디테일하게 챙길 수 있느냐이고, 이런 부분을 챙기는 것이 장점이 될 수 있다.

로그인하지 않은 상태에서 게시물에 좋아요를 누르면 로그인하라는 안내가 나온다. 이때 사용자가 회원가입이나 로그인을 마친 뒤 사이트에서 그 글을 다시 찾아야 한다면 불편하다. 이걸 막는 방법이 여러 가지 있는데, 그중 하나가 쿠키와 callback이고 일반적으로 쿠키를 사용해서 작성한다.

```
비로그인 상태에서 좋아요 클릭 → 로그인 안내
→ 원래 주소를 쿠키 / callback에 저장 → 로그인 또는 회원가입
→ 저장해 둔 주소로 복귀 → 좋아요를 누르려던 글 화면
```

**용어 정리 / 주의점**

- callback = 로그인 같은 절차를 마친 뒤 돌아갈 주소를 알려주는 값
- 링크에 계정 정보를 담으면 주소 기록 등에 남을 수 있으므로, 이 방식은 데모 전용 계정에만 쓰는 것이 안전 (노트에 없는 보충)

### 키워드2: 컴포넌트 구조와 UI 설계

**개념 정리**

리스트 페이지에서 상세보기로 들어가면, 그 카드에 필요한 값은 주소창에서 가져올 수 있다. 그러면 굳이 따로 빼서 넘길 필요가 없고, 리스트와 상세를 한 세트로 쓰는 게 좋다는 설명이었다. UI 단위는 글 좋아요를 하나로 묶고, 댓글 좋아요까지 묶고 싶으면 컴포넌트를 따로 분리해야 한다. 이처럼 구조를 어떻게 나눌지 먼저 생각해야 한다. 값이 필수로 전달되지 않아도 되게 하려면 기본값(default)을 줄 수도 있다.

return은 결과값만 나오는 곳이다. 그런데 return 안에 결과가 아니라 조건 분기가 길게 들어가는 건 지양하는 게 좋다. 가독성도 떨어지고 관리하기도 불편해서, 조건 처리는 return 앞에서 끝내고 return에는 결과만 두자는 방향이다.

```tsx
// 지양: return 안에서 조건 분기가 길어짐
return <div>{isLogin ? (user.isAdmin ? <Admin /> : <User />) : <Guest />}</div>

// 권장: 조건은 return 앞에서 정리하고, return은 결과만
if (!isLogin) return <Guest />
if (user.isAdmin) return <Admin />
return <User />
```

검색 UI에서도 챙길 부분이 있다. 입력한 뒤 지우기를 눌렀을 때 입력값만 지울지, 검색 결과와 페이지까지 초기화할지 정해야 한다.

**용어 정리 / 궁금한 점**

- 기본값(default) = 값이 전달되지 않았을 때 대신 쓰는 값
- 구조를 나눌 때는 UI가 묶이는 단위(글 좋아요, 댓글 좋아요)를 기준으로 생각

### 키워드3: 무한 스크롤과 페이지네이션

**개념 정리**

무한 스크롤은 20페이지까지 내려갔다가 새로고침하면 처음부터 다시 들어가야 하는 단점이 있다. 계속 내리면 로딩 시간이 생겨서 막히기도 한다. 이걸 줄이려는 방법이 1페이지를 부르면서 3페이지를 미리 불러오는 것이고, 부담이 안 되는 선에서 계속 받아오는 방식이다. 또 무한 스크롤은 페이지 관리를 계속 해줘야 하는 단점이 있다. 그래서 상황에 맞게 모바일에서는 무한 스크롤, PC에서는 페이지네이션처럼 나눠서 쓴다.

아키텍처도 구간별로 바꿔야 한다. 한 방식으로 고착화하지 말고 상황에 맞게 유연하게 설계해야 한다.

```
1페이지 요청 → 3페이지까지 미리 불러옴 (부담이 안 되는 선에서)
모바일: 무한 스크롤 / PC: 페이지네이션
```

**용어 정리 / 주의점**

- 무한 스크롤은 새로고침하면 위치를 잃고 페이지 관리가 필요
- 미리 불러오는 양은 서버와 사용자에게 부담이 안 되는 선으로 제한
- 화면 환경(모바일, PC)에 따라 표시 방식을 다르게 설계

### 키워드4: 실시간 통신 (WebSocket, SSE)

**개념 정리**

WebSocket은 클라이언트끼리 연락하는 방식이다. 서버를 띄워 두고 그 정보를 받아서 가져오는 절차를 실행한다. 정리하면 클라이언트와 서버가 연결을 유지하면서, 서버가 한쪽에서 받은 메시지를 다른 클라이언트에게 전달하는 양방향 통신이다.

알림을 받는 서비스는 깊이가 깊어진다. 실시간으로 할지, 집계해서 보여줄지 같은 것을 고려해야 한다. HTTP 통신 방식이지만 이벤트를 통해 알림이 가게 하는 방식이 있는데, 주로 연결이 켜져 있어야 볼 수 있어서 잘 쓰지 않는다. 이 방식이 SSE이고, 프론트엔드에서 쓰는 기술이 EventSource다. 연결이 열려 있다는 건 문이 열려 있는 것이고, 이벤트 소스를 쓰려고 창문을 열어 두는 것과 같아서 주의해야 한다.

EventSource의 문제는 헤더에 값을 담을 수 없다는 점이다. 그래서 Authorization의 Bearer 토큰을 쓰려고 해도 쓸 수 없다. Authorization은 굉장히 보안적인 헤더다. 우회하는 방법으로 토큰을 파라미터로 던지는 방법이 있지만 파라미터가 노출되므로 주의해야 한다. 쿠키를 쓰는 방법도 있지만 알림 기능을 만들 때는 다 좋지는 않다. 강의에서는 Spring의 WebFlux가 라이브 스트리밍 방식의 리액티브 앱이라 그 자체가 SSE 방식이라고 했는데, 강사님도 기억이 정확하지 않다고 했다. SSE가 좋은데 왜 잘 안 쓰는지도 생각해봐야 한다.

```
WebSocket: 클라이언트 ↔ 서버 연결 유지 → 서버가 메시지를 다른 클라이언트에 전달
SSE:       서버 → 클라이언트 이벤트 전달, 프론트엔드는 EventSource로 연결

EventSource에서 토큰 전달 방법
→ 헤더(Authorization)는 사용 불가 / 파라미터는 주소에 노출 / 쿠키는 알림 기능에 다 좋지는 않음
```

| 방법 | 특징 | 주의 |
| --- | --- | --- |
| 파라미터로 토큰 전달 | 쓸 수는 있음 | 주소에 토큰이 노출됨 |
| 쿠키 | 쿠키로 인증 가능 | 알림 기능에는 다 좋지는 않음 |
| 헤더를 지원하는 대체 구현체 | 헤더에 토큰을 담을 수 있음 | 별도 라이브러리가 필요 |

**용어 정리 / 궁금한 점**

- SSE = 서버가 열어 둔 연결로 클라이언트에 이벤트를 보내는 방식, 프론트엔드 기술은 EventSource
- 기본 EventSource는 GET 요청만 보낼 수 있고 payload와 커스텀 헤더를 넣을 수 없다는 점을 라이브러리 문서로 확인
- 궁금한 점: Spring WebFlux가 헤더 문제를 어떻게 피하게 해주는지는 확인 필요

### 키워드5: 채팅 UI 설계

**개념 정리**

채팅의 주체를 채팅방으로 두면 누가 작성했는지만 확인하면 된다. 누가 보내고 누가 받는지의 개념이 필요 없어진다. 그러면 내가 쓴 메시지는 오른쪽에 표시하고 그 외의 모든 ID는 왼쪽에 표시하는 것으로 UI는 해결된다.

채팅을 어디까지 메시지로 볼지도 정해야 한다. 그림과 영상, 시스템 메시지도 채팅으로 봐야 타임라인을 맞추기 쉽다. 그래서 채팅 타입을 text, img, video 같은 식으로 나누면 된다. 채팅 구현은 거의 CSR이다. React는 서버 액션이 없어서 요청이 브라우저에서 나가기 때문에 노출된다.

```
메시지 { id, senderId, type: "text" | "img" | "video" | "system", content, createdAt }  (예시)

senderId === 내 id → 오른쪽 / 그 외 → 왼쪽
```

**용어 정리 / 주의점**

- 메시지는 type으로 나눠서 한 타임라인에 쌓음
- 채팅은 CSR이라 요청 정보가 브라우저에서 보임 (서버 액션은 Next 같은 프레임워크의 서버 기능으로 이해)

## 프로그래머스
```tsx
function solution(sizes) {
    var answer = 0;
    for (let i = 0; i < sizes.length; i++) {
    if (sizes[i][0] < sizes[i][1]) {
        sizes[i].reverse();
    }
}
    let m0 = Math.max(...sizes.map(x => x[0]));
    let m1 = Math.max(...sizes.map(x => x[1]));    
    answer = m0 * m1;
    
    return answer;
}
```
오느까지가 정답률 70퍼 이상의 1레벨 문제로 map을 사용하는 방식이 생각보다 많았으며, 이를 활용만 잘하면 1줄로도 줄일수 있고 코드를 줄이는 것과 가독성은 다르다는 관점이 생겼다. 이 코드를 1줄로 줄이는 코드들은 생각보다 가독성 부분에서 많이 떨어진다.

## 오늘의 회고

SSE는 쉽게 말하면 서버가 연결을 열어 둔 채로 클라이언트에 이벤트를 계속 보내주는 방식이다. 강의에서 EventSource로는 Authorization 헤더에 토큰을 담을 수 없다고 들었는데, 라이브러리 문서를 찾아보니 기본 EventSource는 GET 요청만 보낼 수 있고 payload와 커스텀 헤더를 넣을 수 없었고, 헤더를 넣을 수 있게 만든 대체 구현체와 쿠키를 보내는 withCredentials 옵션이 있었다. 토큰을 파라미터로 넘기면 주소에 노출된다는 점은 강의 설명 그대로 정리했다.
